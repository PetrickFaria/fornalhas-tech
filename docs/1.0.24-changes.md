# Fornalhas Tech 1.0.24

Origin: main, 805d748e351b674744bf05ca75ddcfeab9b254c2 (1.0.23).
Minecraft 1.19.2 / Forge 43.5.0 / Java 17 unchanged.

## Fuel

Existing speeds retained: no core 1; Base 2; Iron 3; Gold 5; Emerald 7;
Diamond 9; Netherite 11. Output and ingredient counts/XP remain unchanged.

Burn and progress use native integer recipe-work ticks. Each productive tick
advances and charges the same work, capped at the remaining recipe work.
For a 200-work recipe, 11x still completes in 19 ticks, as before, but charges
200 burn units rather than 209. No rounding fractions are discarded. Fuel
can be replenished within a tick when the previous fuel runs out, preserving
normal cooking cadence. No tick processes multiple recipes or multiplies output.
Already burning fuel also expires while blocked, at the current speed, like
vanilla's idle burn behavior scaled with the core.

Changing cores changes the next work budget, never the stored burn amount.
Existing integer Burn/BurnTotal/Cook NBT keys retain their meaning. Burning and
productive ticks dirty the entity so chunk unloads persist the current values.
No FE system is introduced. Existing recipe/fuel recognition is preserved.

## Slots / migration

All three menu special slots override maximum stack size to 1. Real inventory
setItem and server-tick normalization enforce this beyond the GUI. The Forge
item capability uses InvWrapper with per-slot limits; its standard insertion
returns leftovers and supports simulation. Existing filters are preserved.
The third slot was already reserved and rejects every item; no enhancer item
or new filter is invented.

Existing special stacks are split into one installed item plus a persistent
SpecialOverflow ListTag. On a server tick surplus is returned as item entities
above the furnace. Queue entries are removed only after successful entity
insertion; the queue is saved and included when the block is broken. No silent
clamping/deletion of legacy surplus. Migration does not consume fuel or alter
customization.

## Light

The block light supplier uses existing CORE and COOKING properties:
no core idle 0 / cooking 5; core idle 10 / cooking 15. Using COOKING rather
than LIT prevents a blocked/finished but still-burning furnace from retaining
processing light. Existing server blockstate updates handle core, processing,
chunk reload changes. Animation does not update world light.

## Textures

Six tech_base_flat_{north,south,west,east,up,down}.png keep 64x64 dimensions.
All grayscale metal pixels above 10 and below 128 gain exactly 32 RGB levels.
This preserves their tonal differences, industrial finish and shading.
Black 0, dark cooking openings 9, light metal, recoloring pixels and alpha are
identical. 10,260 dark-metal pixels are brightened. Masks, animation PNGs,
models, UVs and GUI/item resources are unchanged. Bottom metal is brightened
as requested but is still neither tinted nor animated.

## Verification / limits

Java 17 FuelWorkTest executes the actual FuelWork used by the entity and checks
all seven speeds, unchanged recipe cadence, exact work charge, partial fuel
steps, output yield for multiple fuel durations, core switching, integer
round-trip persistence and overflow bounds. The oak-log 200-work comparison
checks 200 ticks at 1x vs 19 ticks at 11x with the same 200-unit recipe charge;
a 300-unit fuel supports one full recipe plus 100 work at either speed.
This is a unit calculation, not an in-game vanilla/Tech furnace comparison.

The image validator compares every pixel with 1.0.23 and verifies that only the
specified dark grays changed. The six-face preview is an actual PNG contact
sheet, not a Minecraft capture. Existing animation-clock CI test is retained.
